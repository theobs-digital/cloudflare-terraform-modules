# cloudflare-zero-trust-networks

Terraform module that manages the private networks of Cloudflare Zero Trust:
Cloudflare Tunnels and their configuration, WARP Connectors, virtual
networks, CIDR and hostname routes, and the connectivity settings of the
account, on top of the `cloudflare/cloudflare` provider. Every provider
attribute of these resources is available under the same name, and each one
is optional unless the provider or the Cloudflare API requires it: whatever
the caller leaves out keeps Cloudflare's default.

The module hands out the IDs of its virtual networks, which Access
applications and device profiles take, and the tokens that run `cloudflared`
and WARP Connector.

The module is not released yet. The first release will be tagged
`cloudflare-zero-trust-networks/v1.0.0`, see the [CHANGELOG](CHANGELOG.md).

## Usage

```hcl
module "networks" {
  source = "github.com/theobs-digital/cloudflare-terraform-modules//cloudflare-zero-trust-networks?ref=cloudflare-zero-trust-networks/v1.0.0"

  account_id = "023e105f4ecef8ad9ca31a8372d0c353"

  tunnel_cloudflared_virtual_networks = {
    prod = { name = "prod" }
  }

  tunnel_cloudflareds = {
    site_a = { name = "site-a", config_src = "cloudflare" }
  }

  tunnel_cloudflared_configs = {
    site_a = {
      tunnel_id = module.networks.tunnel_cloudflared_ids["site_a"]
      config = {
        ingress = [
          { hostname = "app.example.com", service = "http://localhost:8080" },
          { service = "http_status:404" },
        ]
      }
    }
  }

  tunnel_cloudflared_routes = {
    site_a_lan = {
      network            = "10.0.0.0/24"
      tunnel_id          = module.networks.tunnel_cloudflared_ids["site_a"]
      virtual_network_id = module.networks.tunnel_cloudflared_virtual_network_ids["prod"]
    }
  }
}
```

An object of the module refers to another one through the module's outputs,
as `tunnel_id` and `virtual_network_id` do above: Terraform then knows the
dependency, and the attribute keeps the meaning it has in the provider, an
ID, whether the object lives in this module or elsewhere. The dependency also
orders the deletions: Terraform deletes a route before the tunnel and the
virtual network it uses.

See the [repository README](../README.md#usage) for the SSH form of the
source and the versioning rules.

## Prerequisites

The version constraints are listed under [Requirements](#requirements). The
module is checked with provider 5.28.0, and with Terraform 1.16.5 and 1.3.10.

The provider authenticates with an API token, read from the
`CLOUDFLARE_API_TOKEN` environment variable. The token needs these account
permissions:

| Permission | Operations |
|---|---|
| Account → Cloudflare Tunnel → Edit | tunnels, their configuration and their tokens, virtual networks, CIDR and hostname routes |

They come from the Cloudflare API schema, which lists the permissions each
call accepts. The module is tested with a broader token. The schema lists no
permission for reading a virtual network or a CIDR route by ID, which the
refresh and the import do: that read is checked with the broader token only.

## Tunnels

Each entry of `tunnel_cloudflareds` takes the attributes of
[`cloudflare_zero_trust_tunnel_cloudflared`](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/zero_trust_tunnel_cloudflared).
The key only names the tunnel in the state: renaming a key replaces the
tunnel, that is a new ID and a new token.

### Configuration source

`config_src` tells where the ingress rules of the tunnel live:

- `cloudflare`: in Cloudflare, set by
  [`tunnel_cloudflared_configs`](#remote-configuration);
- `local`, when left out: in the configuration file of `cloudflared`.

Changing `config_src` replaces the tunnel. Write it on every tunnel
configured from Cloudflare, and keep it: left out of a `cloudflare` tunnel,
the plan shows `config_src = "cloudflare" -> "local"` as an in-place update.
Write `config_src` back instead of applying it.

### Tunnel secret

Left out, `tunnel_secret` is generated by Cloudflare. To set your own, at
least 32 bytes in base64, mark the secret sensitive, not the map that holds
it: Terraform refuses a sensitive value in `for_each`, whether the whole map
is wrapped in `sensitive()` or the variable of the module is declared
`sensitive`.

```hcl
variable "site_a_secret" {
  type      = string
  sensitive = true
}

module "networks" {
  # ...

  tunnel_cloudflareds = {
    site_a = { name = "site-a", tunnel_secret = var.site_a_secret }
  }
}
```

The provider declares `tunnel_secret` sensitive, so the plan hides it even
when written in clear. It never reads it back from Cloudflare.

### Run the tunnel

The `tunnel_cloudflared_tokens` output gives the token of each tunnel, by
key. The module reads it at each plan. Pass it to `cloudflared` through the
`TUNNEL_TOKEN` environment variable, which keeps it out of the process list:

```bash
export TUNNEL_TOKEN="$(terraform output -json tunnel_cloudflared_tokens | jq -r .site_a)"
cloudflared tunnel --no-autoupdate run
```

The same command runs a `local` tunnel: `cloudflared` then reads its ingress
rules from its configuration file, given with `--config`.

The state holds the tokens and the tunnel secrets: keep it in an encrypted
backend.

### Public hostname

An ingress rule with a `hostname` creates no DNS record. To serve the
hostname, add a proxied CNAME record to `<id>.cfargotunnel.com`, for instance
with the [`cloudflare-dns`](../cloudflare-dns) module:

```hcl
module "dns" {
  # ...

  records = {
    app = {
      name    = "app"
      type    = "CNAME"
      content = "${module.networks.tunnel_cloudflared_ids["site_a"]}.cfargotunnel.com"
      proxied = true
    }
  }
}
```

### Delete a tunnel

The Cloudflare API deletes a tunnel only when it has no active connection:
stop `cloudflared` before removing the tunnel from `tunnel_cloudflareds`.
Its remote configuration goes with it, although Terraform only forgets the
entry of `tunnel_cloudflared_configs`.

## Remote configuration

Each entry of `tunnel_cloudflared_configs` takes the attributes of
[`cloudflare_zero_trust_tunnel_cloudflared_config`](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/zero_trust_tunnel_cloudflared_config).
`cloudflared` picks a new configuration up while it runs, without a restart.

Configure only tunnels with `config_src = "cloudflare"`. A configuration given
to a `local` tunnel turns it into a `cloudflare` one: `cloudflared` follows the
configuration from Cloudflare and ignores the ingress rules of its file. The
plan shows nothing, since the provider keeps `config_src` from the state, and
writing `config_src = "cloudflare"` afterwards replaces the tunnel.

The rules of `config.ingress` are matched in order, and the last one must
match every request: `service` alone, without `hostname` or `path`, such as
`http_status:404`. The plan does not check it. Cloudflare refuses the apply
otherwise, with `The last ingress rule must match all URLs` (error 1056), and
keeps the previous configuration.

The timeouts of `origin_request`, `connect_timeout`, `keep_alive_timeout`,
`tcp_keep_alive` and `tls_timeout`, are in seconds. Left out, `cloudflared`
uses 30, 90, 30 and 10 seconds, and `keep_alive_connections` defaults to 100.

Cloudflare returns the configuration as written, `false` and empty strings
included: a configuration with every attribute set plans no change after the
apply. `source` is the exception. Leave it out, or write `cloudflare`:
Cloudflare ignores `source = "local"`, and each plan shows it again.

Removing an entry of `tunnel_cloudflared_configs` only drops it from the
state: the tunnel keeps its last configuration, and `cloudflared` keeps
serving it. To change what the tunnel serves, change the entry. A plan that
creates or removes a configuration warns about "Resource Destruction
Considerations": the provider states the same limit, and the warning is
harmless.

## Virtual networks

Each entry of `tunnel_cloudflared_virtual_networks` takes the attributes of
[`cloudflare_zero_trust_tunnel_cloudflared_virtual_network`](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/zero_trust_tunnel_cloudflared_virtual_network).
A virtual network is a separate routing domain: the same CIDR can lead to two
tunnels from two virtual networks. The `tunnel_cloudflared_virtual_network_ids`
output gives their IDs, for the routes of the module and for the private
destinations of Access applications and device profiles. According to
Cloudflare, virtual networks only hold routes to `cloudflared` tunnels, not to
WARP Connectors.

`name`, `comment` and `is_default_network` change in place. Left out,
`comment` is empty.

### Default network

Every account has a virtual network named `default`, which takes the routes
created without `virtual_network_id`. To manage it with the module, import it
with the name, the comment and `is_default_network = true` that Cloudflare
returns, and the plan shows no change. Left out, `is_default_network` is
`false` and `comment` is empty, and the plan wants to change them.

```hcl
import {
  to = module.networks.cloudflare_zero_trust_tunnel_cloudflared_virtual_network.this["default"]
  id = "<account_id>/<virtual_network_id>"
}

module "networks" {
  # ...

  tunnel_cloudflared_virtual_networks = {
    default = {
      name               = "default"
      comment            = "This network was autogenerated because this account lacked a default one"
      is_default_network = true
    }
  }
}
```

The comment above is the one Cloudflare gave the `default` network of the
test account: copy the one of yours.

One network at a time is the default. Setting `is_default_network = true` on
another network takes the role from the current one, whose
`is_default_network` turns `false` in Cloudflare: if the module manages it,
the next plan shows the change. Cloudflare refuses to delete the default
network, `Cannot delete the Virtual Network because: it is the default
virtual network` (error 1049): give the role to another network first.

### Remove a virtual network

Cloudflare deletes a virtual network only once no route uses it, and refuses
otherwise: `Cannot delete the Virtual Network because: virtual network is used
by 5 IP Route(s)` (error 1049), followed by their CIDRs. The state keeps the
network. Routes that take its ID from `tunnel_cloudflared_virtual_network_ids`
make the plan fail with `Invalid index` when the network alone is removed:
remove or move those routes in the same change, and Terraform deletes them
first. The same goes for the tunnels that routes use.

## CIDR routes

Each entry of `tunnel_cloudflared_routes` takes the attributes of
[`cloudflare_zero_trust_tunnel_cloudflared_route`](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/zero_trust_tunnel_cloudflared_route).
Every attribute changes in place: `network`, `tunnel_id`, `virtual_network_id`
and `comment`. Left out, `comment` is empty.

Write `network` as Cloudflare stores it: the first address of the range
(`10.0.0.0/24`, not `10.0.0.1/24`), with a prefix length even for one address
(`10.0.0.5/32`), and IPv6 in its compressed form (`fd00:1::/64`). Cloudflare
accepts the other forms, but returns them rewritten, and each plan then shows
an in-place update.

Left out, `virtual_network_id` is the default network of the account.
Removing it after it was set keeps the route in its network, and the plan
shows no change: to move the route back, write the ID of the default network.

A CIDR can be routed once per virtual network. Cloudflare refuses a second
route for it, `You already have a route defined for this exact IP subnet`
(error 1014), and the state keeps the routes as they were.

## Hostname routes

Each entry of `network_hostname_routes` takes the attributes of
[`cloudflare_zero_trust_network_hostname_route`](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/zero_trust_network_hostname_route).
The provider leaves `hostname` and `tunnel_id` optional, but Cloudflare
refuses a route without them (`missing field`, error 1030): the module
requires them. Every attribute changes in place. A hostname route belongs to
no virtual network, and a hostname leads to one tunnel only: Cloudflare
refuses a second route for it, `Hostname Route already routed to another
tunnel` (error 1108).

Write `hostname` as Cloudflare stores it: lowercase, without a leading or
trailing dot, and without a leading wildcard. Cloudflare stores
`*.internal.example` as `internal.example`, and treats both as the same
hostname. The other forms are accepted, but each plan then shows an in-place
update.

To remove the comment of a hostname route, write `comment = ""`. Left out
after it was set, the comment is sent as `null`, which Cloudflare answers
with a `500 Internal Server Error`; the state keeps the comment.

A hostname route only carries traffic once the devices use the Gateway proxy
and the tunnel runs `cloudflared` 2025.7.0 or later, see
[Connect a private hostname](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/private-net/cloudflared/connect-private-hostname/).
